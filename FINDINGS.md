# Student Voice Kamata security review

Baseline: the Kamata moderation and title releases, before this review's fixes. Line numbers refer to that baseline. This was a source review and an isolated test review. Production configuration and unobserved provider behavior are identified separately.

## High

- **H1 · Teacher authentication can race a password change or session revocation** — `server.js:242–260`, `security.js:105–132,147–177,207–219`. The login verifies one password hash, then `startStaffSession` looks up the account again and stamps the session with the latest hash and revocation epoch. If an old password was accepted just before it was changed, a concurrent login can receive the new hash's session stamp. Binding the session to the credential and epoch actually checked lets the next authorization check reject it. **Fixed and covered by the stale-credential test.**

## Medium

- **M1 · Logged-out sessions can be recreated by an overlapping request** — `security.js:46–63`, `server.js:314–320`. The session store's `touch` method saves the entire session with an insert-or-update. A slow request holding the pre-logout session can put that session back after logout. `touch` only needs to extend the lifetime of a row that still exists. **Fixed and covered by a stale touch/write test.**
- **M2 · Concurrent requests can exhaust the database connection pool** — `profile.js:30–46`, `media.js:29–47`, `security.js:151–175`, `database.js:3–12`. Profile image upload reserves a connection, then asks the pool for another to store the image. The MFA verification path also asks the pool for a second one while holding a transaction. Several simultaneous requests can reserve all five connections and wait on each other. **Fixed for both reviewed paths. Both now reuse their transaction connection.**
- **M3 · One master secret governs user sessions and long-lived teacher enrollment** — `security.js:8–25,46–59,155–165,197–200`, `server.js:40–47`. The session payload and authenticator seed use the same encryption key with different record labels. Replacing the master also breaks older recovery-code checks. Use separate purpose keys and a compatibility window so a planned rotation can preserve enrollment and existing sessions. **Fixed with versioned purpose keys, compatibility tests and a documented rotation procedure.**
- **M4 · Anonymous requests share an MFA attempt bucket** — `server.js:67–77`, `security.js:147–150`. Requests without a login challenge consume a bucket shared by other challenge-less requests. This is narrower than bypassing the authenticator, but makes shared counters easier to abuse and records meaningless MFA attempts. Check for an active challenge before counting an account attempt. **Fixed. Missing challenges are rejected before the account counter.**
- **M5 · Email response timing can differ and email delivery limits are mostly by IP** — `email-auth.js:79–96,124–144`, `server.js:65–77`. Signup returns immediately when Firebase reports an existing account, while a new account triggers a verification email request. Resend performs another provider call when a verification message is required. Similar-looking responses therefore do not guarantee similar timings. Repeated delivery attempts from different networks can also consume the provider quota. Firebase's current email-enumeration setting and quotas were not reverified. **Mitigated with delivery rate limits, generic responses and a minimum response window. Residual timing is possible when Firebase calls exceed the window.**
- **M6 · Comment spam and stored-image growth have no account or total budget** — `server.js:65–72,221–239`, `social.js:77–85`, `media.js:10–40`. Current short IP limits and image validation are useful, but one account can keep writing or uploading over time. A fresh verified email account can publish comments immediately. A cumulative quota and per-account limits address this without depending on the IP header. **Fixed for hosted database media and student writes. Local filesystem capacity remains an operator concern.**
- **M7 · Backup destination validation only excludes `public/`** — `maintenance.mjs:13–25`, `OPERATIONS.md:17–36`. The encrypted backup command and restore drill already exist, and backup files are ignored by Git and Docker. The backup command nevertheless accepts other folders inside the checkout, where a copy, force-add or packaging tool could pick up a snapshot. Require a destination outside the repository and document a separate private directory. **Fixed. The operator refuses a path inside the checkout.**
- **M8 · No full account deletion or public privacy page** — `server.js:281–301`, `database.sql:26–60`, `public/index.html` footer. Trash suspends access and preserves personal fields and existing content. A deletion request therefore cannot be fulfilled via the dashboard today. An irreversible deletion needs a separate, explicit flow, a verified requester, and a policy for articles and backups. **Fixed for application records. Teacher-initiated Firebase credential removal remains an operator step.**
- **M9 · In-flight student writes can cross a ban or revocation** — `server.js:79–103,221–237`, `social.js:18–29,62–85`, `profile.js:29–43`. Authorization is checked before the mutation. A request already underway can complete just after staff bans the account. Rechecking account status and version within the mutation transaction closes this ordering gap. **Fixed by checking student state under the write transaction lock.**

## Low

- **L1 · Proxy hop count is hardcoded** — `server.js:26`, `cloudflare-worker.mjs:10–21`. Express expects one trusted proxy hop in production. The Cloudflare Worker strips incoming forwarding headers before sending to Render, but the effective public client IP and Render's header behavior were not verified in this review. A change in topology can make an IP limit shared or trust the wrong hop. **Fixed with a documented configurable hop count. Live topology is an operator verification step.**
- **L2 · Legacy reset policy differs from login policy** — `server.js:136–148,168–178`. Legacy login already blocks normal access for a weak password and requires an expiring upgrade. Teacher-assisted reset omits the username from the strength check, so it can accept a username-based password that triggers another upgrade at next login. The optional cutoff is a separate policy change. **Fixed. The cutoff remains off by owner choice.**
- **L3 · Documentation has stale deployment and moderation statements** — `README.md:91–95,125,135`. Sessions are encrypted in the database, Render binds to its configured host, comments use the stored alias, and moderation includes Trash. **Fixed for the reviewed deployment and moderation statements.**
- **L4 · Moderation actions flash the sign-in form** — `public/app.js:241–261,294–326`. After a successful change, the page rebuilds the whole dashboard and shows the login panel during network calls. This is a UI reset rather than evidence of a session change. **Fixed by replacing the changed card and tested without changing dashboard/login visibility.**

## Checks without a confirmed vulnerability

- **Authorization boundaries** — `server.js:79–103,263–310`, `profile.js:5–43`, `social.js:39–110`. Profile ownership is taken from the session. Student writes and teacher routes have server-side guards. Existing tests assert that students cannot administer others, guests cannot post, and revoked teacher sessions cannot read unpublished images. See M9 for concurrent revocation.
- **Recovery code expiry and reuse** — `server.js:152–190`, `security.js:147–176`. Legacy reset codes are random, stored as hashes and cleared on use. The reset applies only if the expiry and stored hash match. MFA recovery codes are consumed under a row lock. See H1 and M5 for adjacent risks.
- **Session fixation and cookies** — `server.js:40–47,109–125`, `security.js:121–132`. Successful login replaces the old session ID. Production cookies are `Secure`, `HttpOnly`, and `SameSite=Strict`. See M1 and M3 for session persistence and rotation risks.
- **Validation and encoding** — `server.js:221–237`, `profile.js:5–43`, `media.js:15–57`, `email-auth.js:33–43`, `cloudflare-worker.mjs:5–21`. Reviewed paths use SQL placeholders and render student text with `textContent`. Uploaded file names are generated and checked before reads. Outbound requests use fixed provider hosts. No SQL injection, script injection, arbitrary file read or arbitrary outbound host was found in these paths.
- **Upload validation** — `media.js:9–40`. Uploads have byte and decoded-pixel limits, accept decoded JPEG/PNG/WebP only, and get re-encoded to WebP to remove original metadata. Existing tests cover a disguised SVG and oversized upload. See M2 and M6 for resource abuse.
- **Database rate-store errors** — `server.js:64–77,332–340`, `security.js:67–75`. The limiter uses the package's fail-closed default and the server returns a generic 503 for unrecognized failures. No observed evidence supports a header-based bypass. See L1 for deployment assumptions.
